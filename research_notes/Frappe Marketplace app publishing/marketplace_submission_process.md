# Frappe Marketplace: end-to-end app publishing and approval process (2024–2026)

**Sourcing caveat for the report writer.** In this research environment the domains `docs.frappe.io`, `cloud.frappe.io`, `discuss.frappe.io`, `frappe.io` and `web.archive.org` were blocked at the egress proxy, so their pages could not be fetched directly. Claims attributed to those URLs below come from search-engine excerpts of those pages (quoted text is from the excerpt), not from a full page read. Everything attributed to `github.com` / `raw.githubusercontent.com` (frappe/press source code, frappe/marketplace registry, app PRs) was read directly and is primary. Where a claim rests only on a search excerpt it is marked "(via search excerpt)".

**Big picture (important context for every question below).** As of October 2026 there are *two* co-existing publishing systems:

1. **Frappe Cloud "v1" dashboard marketplace** (cloud.frappe.io/marketplace, previously frappecloud.com/marketplace) – portal-based: publisher account → add app from GitHub → listing fields → submit release → `App Release Approval Request` → automated `Marketplace App Audit` (launched mid-2026) + human approval. Backed by the `frappe/press` codebase.
2. **"The New Marketplace" / Frappe Cloud v2 registry** (github.com/frappe/marketplace, announced on the forum ~Sept 2026) – a GitHub-hosted JSON registry consumed by `frappe/pilot` (the new bench/server manager) and by Frappe Cloud v2. Listing = a pull request; CI (schema → Semgrep → get-app install validator) gates the merge and "once your app passes all automated checks, it goes live immediately without any manual approvals required".

Both are documented below; v1 behaviour from before mid-2026 (purely manual review, 10-day SLA) is marked historical where relevant.

## Key Question 1: Step by step, what does a publisher do to list an app, and what does Frappe review before approval?

### Takeaway
On the v1 Frappe Cloud dashboard the publisher enables a publisher/developer account, adds a GitHub-hosted app they own, picks the Frappe version(s) it supports, fills the listing (logo, ≤140-char summary, long description, screenshots, categories, five support links), submits a release (creates an `App Release Approval Request`, which auto-creates a "Submission Gate" audit), and the app stays Draft/In Review until Frappe approves; on the v2 GitHub registry the publisher instead opens a PR adding `apps.json` metadata + `apps/<name>.json` releases, and automated checks (schema, Semgrep security scan, get-app install test, prebuilt-assets check) are the gate.

- Press periodically runs `auto_review_for_missing_steps` over apps in Draft / Attention Required / In Review and emails the team's Marketplace contacts (template `marketplace_auto_review`, subject "Marketplace App Review: {title}") if logo is missing, description still contains the placeholder "Please add a short", any of website/support/documentation/privacy policy/terms is empty, or no `App Release Approval Request` exists; it links to `/dashboard/marketplace/apps/{app}/review`. — [events.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/events.py)

**Automated audit (v1, launched ~June 2026)**
- Frappe blog (June 10, 2026): an automated "App Auditor" "kicks off the moment you publish a new release", scans "six areas", returns Pass / Warn / Needs Improvement / Fail, and "depending on severity a release may be blocked or flagged for review"; framed as "no more waiting days for a manual review". (via search excerpt) — [Frappe Cloud Release – New deploy experience and more](https://frappe.io/blog/product-updates/frappe-cloud-release-|-deploy-experience-and-more); repeated in [Product Updates for May 2026](https://frappe.io/blog/product-updates/product-updates-for-may-2026)
- The six areas in code: Metadata, Versioning, Dependencies, Code quality, Compatibility, Semgrep rules; audit types `Release Change / Submission Gate / Manual Run / Scheduled Audit`; job status `Queued/Running/Completed/Failed`; verdict `Pass / Needs Improvement / Warn / Fail / Inconclusive`; verdict chain "1. Any Critical Fail -> Fail 2. Any Major Fail/Warn -> Warn 3. Any Minor Fail/Warn -> Needs Improvement 4. Otherwise -> Pass" (code additionally returns Fail when Major fails ≥ warns). Audit runs on the `long` queue with 3600 s timeout. — [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- Consequences (only if Marketplace Settings `enable_audit_actions` is on): a `Fail` auto-rejects every Open approval request with reason starting "Automated audit failed."; if blocking failures exist the release is yanked (`Yanked App Release`), and if no usable release remains the app flips to "Attention Required". The audit never auto-approves. Publisher gets an email report (`marketplace_audit_report`) listing Fail/Warn rows. — [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- **Metadata checks** (what reviewers/auditor look at in the listing): Missing Long Description (Major/Fail); long description containing install instructions such as `bench get-app`, `bench setup`, `git clone` (Minor/Warn, "Please don't add any installation instructions in the description."); containing the words "architecture", "deployment", "installation" (Minor/Warn); containing any `http(s)://` link (Minor/Warn); No Screenshots (Major/Fail); Missing Links – any of website, support, documentation, privacy_policy, terms_of_service empty (Major/Fail, "Please add the missing links for the app to be published on FC."); Broken Links – non 200/301/302 (Major/Warn); No Categories (Minor/Warn, internal-only). — [checks/metadata.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/metadata.py)
- **Semgrep checks**: local rules under `semgrep-rules/`, categories Correctness and Security; severity map CRITICAL/ERROR→Critical, HIGH→Major, WARNING/MEDIUM→Minor, LOW/INFO→Info; category = Fail if any Critical/Major or `is_blocking` finding; example rule `frappe-manual-commit`. — [checks/semgrep_rules.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/semgrep_rules.py)
- **Code-quality checks** (all Major, Warn-only): `override_doctype_class` used (remediation: "Use extend_doctype_class (Frappe v16+) or doc_events hooks instead if possible."), `override_whitelisted_methods` used, wildcard `"*"` in `doc_events` ("can impact performance on shared benches"). — [checks/code_quality.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/code_quality.py)

**v2 GitHub registry flow (frappe/marketplace)**
- Forum announcement (~Sept 2026): "The new Marketplace now resides on GitHub at frappe/marketplace"; listings "managed directly via Pull Requests ... using two files: apps.json, which acts as the global registry to index primary app metadata, and apps/<app-name>.json, which tracks specific version releases, compatible version ranges, and commit references"; "every app submitted to the marketplace will automatically run through a series of continuous checks and validations" (syntax/import validation, hooks and repository structure checks, symlinks/fixtures…); "once your app passes all automated checks, it goes live immediately without any manual approvals required"; the registry is built into frappe/pilot and reached by every VM "whether hosted on Frappe Cloud or self-hosted". (via search excerpt) — [The New Marketplace](https://discuss.frappe.io/t/the-new-marketplace/164661)
- README: "Add a metadata entry to `apps.json`, add `apps/<name>.json` with at least one release, and open a PR." Alternative: call the reusable `publish-release.yml` workflow from your repo, which reads `version`, `frappe_core`, `dependencies` from `pyproject.toml` and opens the PR; or run `tools/add_release.py`. — [frappe/marketplace README](https://github.com/frappe/marketplace)
- `apps.json` entry fields: `name` (required, unique snake_case), `title`, `description`, `repo` (public GitHub URL), `logo_url` (square PNG/SVG), `website`, `documentation`, `categories` (UI tags e.g. `Featured`), `category` (one of Applications, Compliance, Developer Tools, Extensions, Integrations, Utilities), `stars` (synced by script), `releases` (must be exactly `apps/<name>.json`). — [frappe/marketplace README](https://github.com/frappe/marketplace)
- `schema_check.py` actually requires `name, title, description, repo, logo_url, website, documentation, category` to be truthy, `categories` to be a non-empty list, `stars` an integer, releases list non-empty, and per release `version, branch, commit, frappe_core` truthy and `dependencies` a dict (`{}` allowed). — [validation/schema_check.py](https://github.com/frappe/marketplace/blob/main/validation/schema_check.py)
- CI order: schema → Semgrep → get-app validator, stopping at first failure. Semgrep blocking findings "include code injection, template injection, SQL injection, command execution, authorization bypass, and multitenancy violations"; WARNING-level findings reported but non-blocking. Severities Critical/Major/Minor/Info; "Critical and Major block the merge". CI posts one PR comment (edited on each push); fork PRs only get the run summary; comment `/rereview` to re-run. — [frappe/marketplace README](https://github.com/frappe/marketplace); [validation/semgrep_check.py](https://github.com/frappe/marketplace/blob/main/validation/semgrep_check.py)
- get-app validator: requires `pyproject.toml` at the commit; advertised `version` must equal `project.version` (or `__version__` in `__init__.py` if dynamic); advertised `frappe_core` must equal `tool.bench.frappe-dependencies.frappe`; picks Frappe branch from the highest lower bound's major (`>=15.x` → `version-15`); creates a throwaway bench + venv and runs Pilot's `InstallValidator` ("repo structure, syntax, dependency declaration, and a real `uv pip install`"); requires a prebuilt asset `.tar.gz.sha256` in a GitHub release tagged from the branch name. — [validation/get_app_check.py](https://github.com/frappe/marketplace/blob/main/validation/get_app_check.py)
- Real-world throughput: on Oct 19–20, 2026 the registry merged ~12 "advertise <sha>" PRs for gameplan, raven, etc. the same day they were opened; PRs #40, #41 (gameplan) and #37 (insights "Cap releases to the Frappe versions they build on") were closed unmerged (no stated reason). — [frappe/marketplace pulls](https://github.com/frappe/marketplace/pulls?q=is%3Apr)
- Worked example of passing the v2 checks (Kamra PMS, merged Oct 12, 2026): the registry "reads `__version__` verbatim" so a release-please inline marker produced `2.6.10"  # x-release-please-version` and broke the version check; absolute-path symlinks under `.claude/skills` failed and were made relative; `payments = ">=0.0.1,<1.0.0"` was added under `[tool.bench.frappe-dependencies]` to mirror `required_apps`; Semgrep passed with 244 advisory, 0 blocking findings; author ran the registry CI locally first. — [Kamra-PMS/kamra-pms PR #159](https://github.com/Kamra-PMS/kamra-pms/pull/159)

### Inferences
- In practice (v1) "what Frappe reviews" = listing hygiene (logo, 140-char summary, long description without install steps/links, screenshots, five links, categories), the pyproject/hooks conventions in Q2, a Semgrep security scan, and—for new apps from unknown publishers—a human look at the code diff. Only Critical-severity audit failures hard-block; most other findings are advisory.
- The press `review_stage` field and "Code Screening" fields were dropped (patch `cleanup_code_screening_data.py` nulls them), suggesting an earlier LLM/code-screening experiment was replaced by the Semgrep-based audit — [cleanup_code_screening_data.py](https://github.com/frappe/press/blob/master/press/marketplace/patches/cleanup_code_screening_data.py).
- The v2 registry is already the primary path for Frappe's own apps (helpdesk, gameplan, raven, lms, insights) as of Oct 2026; third-party developers (Kamra, navari, ERPGulf) are also listed, so it is live for third parties.

### Gaps
- The exact wording of the docs pages (publishing-an-app, guidelines, authoring-guidelines, manage-marketplace-app) could not be read directly (domain blocked); only search excerpts.
- No official statement found on whether v1 dashboard submissions are still accepted or when v1 will be retired, nor on whether existing v1 listings are auto-migrated to the v2 registry (a Sept 2025 WG note said migrating existing listings was "the first order of business", status unknown).
- The list of Semgrep rule IDs in press `semgrep-rules/` and marketplace `validation/semgrep-rules/` was not enumerated.

## Key Question 2: Which repo/branch/version conventions are required (branch naming, frappe pin, required_apps, version in __init__.py, hooks, pyproject)? Must the app be at the repo root?

### Takeaway
A root-level `pyproject.toml` with `[tool.bench.frappe-dependencies] frappe = ">=X.0.0-dev,<Y.0.0"` (a bounded *range*, not an exact pin, with frappe NOT in `[project.dependencies]`), `[project] version` (or `__version__` in `<app>/__init__.py` as fallback), a `hooks.py` whose `app_name` equals the package directory and whose `required_apps` is a plain list of string literals (mirrored as version ranges in `frappe-dependencies`), no symlinks, no side-effects in `__init__.py`, and prebuilt JS/CSS assets published to a GitHub release (`assets-<branch>`) are the hard requirements; branch names are free (helpdesk uses `main` + `develop`, blog uses `version-16`) and the app must be a standalone GitHub repo with `pyproject.toml` at the root (no monorepo/subdirectory support found).

### Cited Findings

**pyproject / frappe dependency pin**
- Official versioning doc: every app needs a root-level `pyproject.toml` declaring a bounded Frappe range under `[tool.bench.frappe-dependencies]`; Frappe Cloud uses it during bench update, app install and bench-group addition; docs show `>=16.0.0-dev,<=17.0.0` while the custom-app page shows `>=16.0.0-dev,<17.0.0`; forum: multiple constraints must be comma-separated with no space. (via search excerpt) — [Versioning](https://docs.frappe.io/cloud/custom-apps/app-versioning/versioning); [How to install a custom app](https://docs.frappe.io/cloud/benches/custom-app); [Versioning and Custom App Rules](https://discuss.frappe.io/t/versioning-and-custom-app-rules/160252)
- Press audit versioning checks: `ver_pyproject_exists` (Critical, stops run: "pyproject.toml not found at the root of the app"); `ver_pyproject_valid_syntax` (Critical); `ver_frappe_deps_section` (Critical: "Missing [tool.bench.frappe-dependencies] section in pyproject.toml", remediation example `frappe = ">=16.0.0-dev,<=17.0.0-dev"`); `ver_frappe_version_specifier` (Critical: valid semver range required); `ver_no_frappe_in_project_deps` (Major: "frappe found in [project.dependencies] — this will cause build failures"); `ver_no_other_apps_in_project_deps` (Major: `erpnext`, `frappe-bench`, `crm`, `hrms` must not be in project deps); `ver_app_version_declared` (Minor Warn: "No version found in pyproject.toml or __init__.py"); `ver_no_dual_dep_files` (Info Warn if `requirements.txt` also present, "pyproject.toml takes precedence"); `ver_no_hard_pinned_frappe` (Minor Warn: "Frappe is hard-pinned to: {spec}", use a range). — [checks/versioning.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/versioning.py)
- Version source order: `[project] version` first; fallback is a line starting `__version__ =` or `VERSION =` in an `__init__.py` one directory deep. — [checks/versioning.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/versioning.py)
- v2 registry: "`frappe_core` ... Must come from `[tool.bench.frappe-dependencies].frappe` in `pyproject.toml`"; releases without it are rejected; `dependencies` is `{name: version-range}` of other marketplace apps and `{}` is allowed but the key must exist. — [frappe/marketplace README](https://github.com/frappe/marketplace)
- `tools/add_release.py` reads `project.version` (fallback `<project.name>/__init__.py` `__version__`), and turns `[tool.bench.frappe-dependencies]` into `frappe_core` (the `frappe` key) + `dependencies` (all other keys); it never reads `hooks.py`. — [tools/add_release.py](https://github.com/frappe/marketplace/blob/main/tools/add_release.py)
- Example registry release (helpdesk): stable 1.30.1 on branch `main`, `frappe_core ">=15.116.1,<17.0.0"`, dependency `telephony ">=0.0.1,<1.0.0"`; nightly 1.22.2 on `develop`, `">=16.0.0-dev,<18.0.0"`. — [apps/helpdesk.json](https://github.com/frappe/marketplace/blob/main/apps/helpdesk.json)

**hooks.py / required_apps / repo hygiene**
- Press audit dependency checks: `dep_hooks_exists` (Critical, blocking: "hooks.py not found in the app"); `dep_hooks_syntax` (Critical); `dep_no_symlinks` (Critical, blocking: "symlinks cause build errors"); `dep_init_side_effects` (Major, blocking: top-level bare calls like `print()` in `__init__.py` "run on every bench command"); `dep_app_name_consistency` (Critical: `app_name` in hooks.py must equal the package directory name); `dep_required_apps` (Major: must be "a plain list of string literals, e.g. `required_apps = ["erpnext"]`"; Warn if it includes `frappe`, duplicates or empty strings). — [checks/dependencies.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/dependencies.py)
- Frappe Cloud "Required app not found" doc: a missing dependency can be declared in either `hooks.py` (`required_apps`) or `pyproject.toml`. (via search excerpt) — [Required app not found](https://docs.frappe.io/cloud/common-issues/required-app-not-found)
- v2 README (aakvatech mirror wording): the get-app validator catches "broken repo structure, syntax errors, undeclared `[tool.bench.frappe-dependencies]`/`required_apps` mismatches, plus missing imports and dependencies". — [aakvatech/marketplace README](https://github.com/aakvatech/marketplace)
- App authoring guideline: avoid overriding base Frappe pages such as login; extend behaviour through hooks; a passing GitHub Actions CI in the repo is listed as an approval condition. (via search excerpt) — [App authoring guidelines](https://docs.frappe.io/cloud/marketplace/app-authoring-guidelines); [Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)

**Branches and Frappe versions**
- v1: each `Marketplace App Version` source row = (repository_owner, repository, branch, version); `validate_frappe_version_for_branch()` reads the pyproject frappe spec from GitHub and throws "{version} is not supported by branch {branch} for app {app_name}" if the chosen Frappe Version isn't covered; `ease_versioning_constrains=True` means a lower-bound spec like `>=16.15.0,<17` counts as supporting Version 16. — [marketplace_app.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.py); [checks/compatibility.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/compatibility.py)
- Compatibility audit: `compat_bench_versions` (Critical, blocking) fails if any enabled Release Group using this source runs a Frappe version outside the spec ("deployments will fail"); `compat_registered_source_version` (Critical, blocking) fails if the marketplace-registered Frappe version for the source isn't covered by the pyproject spec. — [checks/compatibility.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/compatibility.py)
- Listing pages show "Supported versions" (e.g. Wiki: Version 13–16 + Nightly; CRM: Version 16, Version 15, Nightly). (via search excerpt) — [cloud.frappe.io/marketplace/apps/wiki](https://cloud.frappe.io/marketplace/apps/wiki); [cloud.frappe.io/marketplace/apps/crm](https://cloud.frappe.io/marketplace/apps/crm)
- v2: `branch` = "Branch Pilot tracks for updates"; `commit` = full 40-char SHA reachable from branch; `channel` = `stable` (default) or `nightly`; "`channel` describes the code line, not the branch name"; "Apps with only a `develop` branch should use `stable`"; "One release per branch is the norm"; a branch cannot hold two releases with the same version. Pilot "installs the newest compatible `stable` release" and "only falls back to `nightly` when no stable release fits the bench's Frappe version." — [frappe/marketplace README](https://github.com/frappe/marketplace)
- Prebuilt assets: apps add an `assets.yml` workflow calling `frappe/pilot/.github/workflows/app-assets.yml`, which builds against a Frappe version and uploads `<app>-<sha>.tar.gz` + `.sha256` to a GitHub release tagged `assets-<branch>`; benches download these instead of building. Examples: `assets-main` (helpdesk, crm, raven), `assets-develop` (suite), `assets-version-16` (blog). — [frappe/insights PR #1495](https://github.com/frappe/insights/pull/1495); [frappe/lending PR #1493](https://github.com/frappe/lending/pull/1493); [helpdesk assets-main release](https://github.com/frappe/helpdesk/releases/tag/assets-main); [blog assets-version-16](https://github.com/frappe/blog/releases/tag/assets-version-16)

**Repo root / monorepo**
- Frappe Cloud forum answer (~2024): "As of today, Frappe Cloud doesn't support Monorepos". (via search excerpt) — [Hosting Custom Apps in Monorepo on Frappe Cloud](https://discuss.frappe.io/t/hosting-custom-apps-in-monorepo-on-frappe-cloud-is-it-supported/130028)
- Press code requires each source to be a (repository_owner, repository, branch) triple and reads README/pyproject from the repo root; no subdirectory field exists on Marketplace App / App Source in the code read. — [marketplace_app.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.py)
- v2 validator: "A `pyproject.toml` must exist at the commit" (root), app symlinked into the bench `apps/` directory as a whole clone; no subdirectory option. — [validation/get_app_check.py](https://github.com/frappe/marketplace/blob/main/validation/get_app_check.py)
- Guidelines: "the app should be hosted on GitHub" and "you must be the owner"; app names must be unique across the marketplace. (via search excerpt) — [Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)

### Inferences
- Branch names like `version-14`/`version-15` are convention, not requirement; what matters is that each branch's `pyproject.toml` frappe range resolves to the Frappe Version(s) you register it for, and (v2) that one release-per-branch is advertised per commit.
- Version-14 support: no mention of v14 anywhere in the 2026 sources; all examples target v15/v16/nightly, and "current stable" is the guideline wording, so publishing a v14-only app in 2026 is likely to fail the "support the current stable version" guideline.
- Subdirectory apps are not supported in either system; the app package must be a standalone repo with `pyproject.toml` at the root and `hooks.py` inside `<app_name>/`.

### Gaps
- Exact Frappe-Version-to-range mapping (`map_frappe_version`) internals not read.
- Pilot's `InstallValidator` rules (what counts as "broken repo structure", "fixtures" check) and the `app-assets.yml` workflow inputs were not read directly.

## Key Question 3: Are closed-source / proprietary apps allowed on the marketplace? Under what conditions?

### Takeaway
No. Both the Frappe Cloud v1 guidelines and the v2 registry require a public GitHub repository; v1 docs state apps "must be MIT or compatible with the GNU General Public License" (FSF GPL-compatible list), and this applies to paid apps too—monetisation is via paid plans (80/20 after the first $500) or the 25% free-app revenue-share pool, not via proprietary licensing.

### Cited Findings
- Frappe Cloud marketplace overview: apps must be MIT-licensed or compatible with the GPL, pointing to the FSF list of GPL-compatible licenses; publishers who don't meet this are rejected; publisher must own the app and it must be hosted on GitHub. (via search excerpt) — [Frappe Cloud Marketplace Overview](https://docs.frappe.io/cloud/marketplace)
- Guidelines: "They must be MIT or compatible with the GNU General Public License"; also "valid contact information" and support for "the current stable version of Frappe/ERPNext". (via search excerpt) — [Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)
- v2 registry: `repo` field is a "Public GitHub repo URL" (required); the validator clones it anonymously in CI. No `license` field exists in `apps.json`. — [frappe/marketplace README](https://github.com/frappe/marketplace); [apps.json](https://github.com/frappe/marketplace/blob/main/apps.json)
- Forum thread (Sept 2026) by an independent developer notes marketplace apps "must be open source, including paid apps" and asks what the business model for standalone commercial products is; no maintainer reply visible in the excerpt. (via search excerpt) — [Genuine question: what is the intended business model for independent Frappe app developers?](https://discuss.frappe.io/t/genuine-question-what-is-the-intended-business-model-for-independent-frappe-app-developers/164881)
- Paid-app economics: "Frappe Cloud takes the first $500 of the revenue the app makes. After that the payment will be split 80-20, where 80% will go to you and 20% to Frappe Cloud", effective 1 April 2023. (via search excerpt) — [Payouts](https://docs.frappe.io/cloud/marketplace/payouts); [Grow with Frappe Cloud and Marketplace](https://frappe.io/blog/frappe-cloud/grow-with-frappe-cloud-and-marketplace)
- Free-app revenue share (announced ~Sept 2025): Frappe "will share 25% of its top-line hosting revenue with all app developers on the Frappe Cloud marketplace", distributed by "app complexity, dependency on other apps, and required marketing efforts"; developers must opt in and be approved; motivated by developers keeping apps private "due to monetization challenges". (via search excerpt) — [Revenue sharing with 3rd party apps](https://frappe.io/blog/announcements/revenue-sharing-with-3rd-party-apps-on-frappe-cloud-marketplace); third-party summary says payouts quarterly — [Blackslate](https://www.blackslate.io/news/frappe-cloud-revenue-sharing-program-for-free-and-open-source-apps)
- Press supports `subscription_type` Free / Paid / Freemium and Marketplace App Plans (`create_app_plan`, "Plan features can't be blank."); subscriptions are listed to publishers. — [marketplace_app.json](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.json); [press/api/marketplace.py](https://raw.githubusercontent.com/frappe/press/master/press/api/marketplace.py)
- Frappe licence policy context: Framework MIT, ERPNext GPLv3, CRM/Helpdesk AGPLv3; forum discussion notes AGPL can reach network-delivered apps and leaves open whether a proprietary app can coexist with AGPL apps on a site. (via search excerpt) — [License and Trademark](https://docs.frappe.io/legal/others/license-and-trademark); [Frappe Licensing & Software Architecture](https://discuss.frappe.io/t/frappe-licensing-software-architecture/120722)

### Inferences
- A proprietary-licensed app cannot be listed; the practical options are (a) open-source the Frappe app and sell a paid plan or hosted service, or (b) keep the app private and install it as a "custom app" on customers' private benches outside the marketplace (Frappe Cloud supports private GitHub repos for custom apps via the GitHub App installation, per `github_installation_id` in press).
- Semgrep/get-app CI in v2 requires an anonymously cloneable repo, so even a "source-available but private" repo is technically excluded.

### Gaps
- No explicit written statement found that the v2 registry enforces an OSI/GPL-compatible licence (it enforces *public repo*, and the v1 docs enforce licence); whether v2 maintainers reject PRs for non-OSI licences is unverified.
- Whether paid plans/billing exist yet in the v2 registry (apps.json has no pricing fields) is unknown.

## Key Question 4: How are app updates and new releases handled for sites that installed from the marketplace?

### Takeaway
v1: each new commit creates an App Release; the publisher submits it (Draft → Awaiting Approval → Approved/Rejected), an audit runs, and once approved the release is deployed to the public shared benches (shared-bench sites auto-upgrade; private benches show "Update Available" and the owner picks apps/sites and deploys, ~20 min with downtime); failed audits can *yank* a release so it is never offered. v2: a release is one immutable commit advertised via PR; Pilot tracks the `branch` and installs the newest compatible `stable` release, with `nightly` fallback.

### Cited Findings
- v1 release states: "An app release can be in one of the 4 states" Draft, Awaiting Approval, Approved, Rejected; "Once approved, the release will be deployed to marketplace within a week." (via search excerpt) — [Managing your Marketplace App](https://docs.frappe.io/cloud/marketplace/manage-marketplace-app); [internal review process](https://cloud.frappe.io/internal/press/marketplace)
- Press: `create_approval_request(name, app_release)` sets the release to "Awaiting Approval"; `releases()` lists releases with rejection feedback; `latest_approved_release(source)` returns the newest approved; `reason_for_rejection()` ("This app release wasn't rejected, so there is no rejection reason to show."). — [press/api/marketplace.py](https://raw.githubusercontent.com/frappe/press/master/press/api/marketplace.py)
- Yanking: `yank_app_release()`/`unyank_app_release()` create/delete a "Yanked App Release" for a commit hash; the audit auto-yanks on blocking failures (only if release is Draft or Approved). — [marketplace_app.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.py); [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- Frappe Cloud docs on yanked releases: a withdrawn marketplace release "should not be installed or used for updates"; if selected "you need to choose a valid, non-yanked release". (via search excerpt) — [Updating a Bench](https://docs.frappe.io/cloud/benches/updating_a_bench)
- Site/bench update UX: users "receive a prompt when a new upgrade is available in any of the apps installed on your site"; bench dashboard shows an update banner and "Show Updates" dialog to choose which apps to update; on private bench groups click "Update Available", select apps, then sites, "Deploy and Update"; deploy "usually takes around 20 mins" with some downtime; "Applications hosted on shared benches are always set on auto-upgrade", private benches can toggle auto-updates per site; App Patch feature for small fixes. (via search excerpt) — [Installing an app](https://docs.frappe.io/cloud/installing-an-app); [Updating a Bench](https://docs.frappe.io/cloud/benches/updating_a_bench); [Update an app/site on a private bench](https://docs.frappe.io/cloud/sites/how-to-update-an-app-site-on-a-private-bench)
- Audit "Release Change" type runs per new release and "Scheduled Audit" periodically; old audit records cleared monthly. — [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- v2: "Releases are commit-scoped. Pushing to a branch publishes nothing; every version lands through a gated PR." Apps whose version never changes "edit their single release entry in place". `add_release.py`: same-commit → no-op; same version+branch → replaced; releases sorted newest first. — [frappe/marketplace README](https://github.com/frappe/marketplace); [tools/add_release.py](https://github.com/frappe/marketplace/blob/main/tools/add_release.py)
- v2 automation: app repos call `uses: frappe/marketplace/.github/workflows/publish-release.yml@main` with inputs `app`, `branch`, optional `commit`, `channel`, secret `registry_token` (PAT able to push a fork branch and open a PR); it runs `add_release.py`, creates branch `publish/<app>-<sha8>`, commits as github-actions[bot], opens a PR to `main`; "the marketplace's own checks still gate the merge". Frappe's gameplan releases "every merge to develop" this way. — [publish-release.yml](https://github.com/frappe/marketplace/blob/main/.github/workflows/publish-release.yml); [frappe/gameplan PR #616](https://github.com/frappe/gameplan/pull/616)
- Forum: commit-based releases "prevent branch-scoped bugs from carrying into newer updates". (via search excerpt) — [The New Marketplace](https://discuss.frappe.io/t/the-new-marketplace/164661)

### Inferences
- For a publisher the practical cadence is: tag/merge → (v1) submit release in dashboard and wait for audit+approval, or (v2) let the reusable workflow open the registry PR after the `app-assets.yml` run finishes for that commit → sites pick it up on their next bench update (auto on shared benches).
- Because v2 Pilot resolves "newest compatible stable" by `frappe_core` range, publishers must keep separate release entries per Frappe major (e.g. a `version-15` branch release with `>=15,<16` and a `main`/`version-16` release with `>=16,<17`).

### Gaps
- No source describing how v2 Frappe Cloud notifies site owners of new registry releases, or whether v2 benches auto-update.
- Not confirmed whether v1's "deployed within a week" still applies post-auditor.

## Key Question 5: Typical timelines, support expectations, and common rejection reasons

### Takeaway
Official v1 target was 10 days (historical), but 2025–2026 forum reports show 2 weeks to 2+ months "In Review" with no feedback; the June 2026 auditor and the Sept 2026 v2 registry (same-day merges) are Frappe's answers. Common blockers are listing-hygiene (install instructions/links in the long description, missing screenshots or any of the five links, placeholder description), pyproject/hooks problems (missing `[tool.bench.frappe-dependencies]`, frappe in project deps, `app_name` mismatch, symlinks, version string mismatch), missing prebuilt assets (v2), and Semgrep Critical/Major security findings.

### Cited Findings
- Timeline (official, historical): "Apps will be reviewed or published in 10 days time"; raise a Support Portal ticket afterwards. (via search excerpt) — [Publishing an App to Marketplace](https://docs.frappe.io/cloud/marketplace/publishing-an-app-to-marketplace)
- Forum (~Jan 2026): "status had been almost the same for >2 weeks"; a commenter attributed delays to Frappe revamping the review process; the developer cancelled submissions to resubmit newer versions. (via search excerpt) — [How long does it usually take for Marketplace to release a version of my app?](https://discuss.frappe.io/t/how-long-does-it-usually-take-for-marketplace-to-release-a-version-of-my-app/159324)
- Forum (~mid 2026): app "under review for almost 2 months with no clear update"; another reply: more than three weeks "In Review" with no feedback; a commenter says "there is an operational issue in the review timeline". (via search excerpt) — [Marketplace App Review Delayed (2 Months) – Need Guidance](https://discuss.frappe.io/t/marketplace-app-review-delayed-2-months-need-guidance/162144)
- Forum (~Sept 2026): audit report flagged one issue—"long description contained install instructions"; after removal the app remained in Review State for almost two weeks. (via search excerpt) — [App is in Review state not Publishing](https://discuss.frappe.io/t/app-is-in-review-state-not-publishing/164818)
- Community complaint that many listings lack information; request for screenshots and "if possible, a video". (via search excerpt) — [Marketplace apps should have enough information](https://discuss.frappe.io/t/marketplace-apps-should-have-enough-information/163247)
- Guideline content rules (rejection grounds): logo must be a custom image ≥200×200 px, cropped to a square, shown in a circular frame, avoid text in logos; short description 40–80 chars, one sentence; "Don't repeat the short description in the long description"; no installation instructions ("Frappe Cloud automatically handles those"); screenshots go in the screenshot section not the long description; app must provide value, must not steer users away from Frappe Cloud; valid publisher contact info; support and privacy-policy URLs required; a short demo video is recommended/may be requested; passing GitHub Actions CI; support current stable Frappe/ERPNext. (via search excerpt) — [Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)
- Automated rejection text: "Automated audit failed." + result + summary, applied to all Open requests when the audit verdict is Fail. — [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- Critical/blocking audit conditions (hard fails): no `pyproject.toml` at root, invalid TOML, missing `[tool.bench.frappe-dependencies]`, invalid frappe specifier, missing/invalid `hooks.py`, symlinks in the tree, `app_name` ≠ package dir, side-effect calls in `__init__.py` (Major, blocking), bench/registered-version incompatibility, Semgrep Critical/Major. Major non-blocking fails: missing long description, no screenshots, missing links, frappe/erpnext in `[project.dependencies]`, unparsable `required_apps`. — [checks/versioning.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/versioning.py); [checks/dependencies.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/dependencies.py); [checks/metadata.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/metadata.py); [checks/compatibility.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/compatibility.py)
- v2 CI failure messages: non-reachable commit, version or `frappe_core` mismatch with the commit's pyproject, non-full SHA, missing prebuilt asset (pointer to the assets workflow), unreachable asset URL, asset-check timeout (suggests `/rereview`). — [validation/get_app_check.py](https://github.com/frappe/marketplace/blob/main/validation/get_app_check.py); [frappe/marketplace README](https://github.com/frappe/marketplace)
- v2 real-world: third-party Kamra PMS release was blocked by a release-please version marker and absolute symlinks; fixed and merged Oct 12, 2026. — [Kamra-PMS PR #159](https://github.com/Kamra-PMS/kamra-pms/pull/159)
- v2 throughput: multiple registry PRs opened and merged same day (Oct 19–20, 2026). — [frappe/marketplace pulls](https://github.com/frappe/marketplace/pulls?q=is%3Apr)
- Support expectations: `support` URL is mandatory (Missing Links = Major Fail); press provides a per-app review communication thread (`communication()`/`add_reply()`) and emails on approve/reject; publishers get an audit report email. — [press/api/marketplace.py](https://raw.githubusercontent.com/frappe/press/master/press/api/marketplace.py); [marketplace_app_audit.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/marketplace_app_audit.py)
- "Verified"/"compatible" badges: no "Frappe Approved" or "verified" badge is documented publicly; the `frappe_approved` checkbox exists on the doctype's Review tab (no logic found in the controller); listings show a "Featured" tag (ERPNext, CRM, Learning, Wiki) and a "Supported versions" list; in v2 `categories` can include `Featured` and the "Featured App" list in Marketplace Settings auto-approves releases. (via search excerpt + code) — [marketplace_app.json](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.json); [cloud.frappe.io/marketplace/search](https://cloud.frappe.io/marketplace/search); [frappe/marketplace README](https://github.com/frappe/marketplace); [app_release_approval_request.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/app_release_approval_request/app_release_approval_request.py)

### Inferences
- Explicit "Rejected" outcomes are rarely reported publicly; the dominant community complaint 2025–mid-2026 was silence/delay, not rejection. With the auditor, most "rejections" are now automated and self-explanatory (audit report email).
- "Compatible" on a listing is derived mechanically from the pyproject frappe range per source branch, not a human badge; "Featured" is a Frappe-curated tag that also confers auto-approval.

### Gaps
- No official current (post-June-2026) SLA for v1 human review found.
- No public list of what earns "Featured".
- Full text of forum threads could not be read (domain blocked), so reply-level detail (e.g. staff responses in the 2-month thread) is unverified.
