# Frontend bundling and Desk integration for a React chart library in Frappe (v15 / v16, 2024-2026)

Research method note: Frappe's own documentation hosts (docs.frappe.io, frappeframework.com) and the forum (discuss.frappe.io) were unreachable from this environment (DNS/proxy refusals), so almost every finding below is cited to primary source code on GitHub (frappe/frappe `develop` = v16 line and `version-15`, frappe/press = Frappe Cloud's open-source control plane, frappe/bench, frappe/frappe-ui, frappe/insights, frappe/helpdesk, frappe/crm, frappe/gameplan). Forum/doc findings come from search-result snippets only and are marked as such. Code was read on 2026-10-20; line references are approximate.

## Key Question 1: Canonical way (2025-2026) to ship a prebuilt React bundle inside a Frappe app that installs cleanly on Frappe Cloud; does Frappe Cloud run a Node build, under what conditions; constraints

### Takeaway
Frappe Cloud does run Node: its Docker build template installs Node via nvm plus yarn, then runs `bench get-app` for every app, which runs `yarn install --check-files` whenever the app root has a `package.json` and then `bench build` (esbuild for `*.bundle.js` entries, plus the app's own `package.json` `scripts.build` such as a Vite build). So the canonical pattern is: commit source + lockfile, `.gitignore` the Vite output under `<app>/public/<dir>` and the generated `www/*.html`, and let the bench build produce them; the main failure modes are Node `engines` mismatch, Node heap OOM for big Vite builds, and missing `yarn install` before `yarn build`.

### Cited Findings
- Frappe Cloud's image build template installs Node with nvm (`nvm install ${NODE_VERSION}`), installs yarn globally (`npm install -g yarn`), runs `bench init` for frappe and then, for every other app in the release group, `bench get-app file:///home/frappe/context/apps/<app>` (or a cached-asset path `get_cached_app.py <app> <hash>` when `use_cached` and the asset store are enabled). It ends by setting `ENV FRAPPE_HARD_LINK_ASSETS True`. — [frappe/press press/docker/Dockerfile](https://github.com/frappe/press/blob/master/press/docker/Dockerfile)
- `bench get-app` / `install_app` in bench runs `pip install -e <app>`, then `if not using_cached and os.path.exists(os.path.join(app_path, "package.json")): bench.run("yarn install --check-files", cwd=app_path)`, then `build_assets(bench_path, app=app, using_cached=using_cached)` unless `skip_assets` is set. — [frappe/bench bench/app.py (install_app)](https://github.com/frappe/bench/blob/develop/bench/app.py)
- Frappe's esbuild driver (`node esbuild`) globs every app's `public/**/*.bundle.{js,ts,css,sass,scss,less,styl,jsx}` (ignoring `public/node_modules` and `public/dist`), bundles with `entryNames: "[dir]/[name].[hash]"`, `minify: PRODUCTION`, `define: process.env.NODE_ENV = "production"|"development"`, and writes output to `sites/assets/<app>/dist/{js,css}/`. In v16 the target is `es2020` (configurable with `--esbuild-target`); in v15 the target is `es2017`. — [frappe/frappe esbuild/esbuild.js (develop)](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js); [version-15](https://github.com/frappe/frappe/blob/version-15/esbuild/esbuild.js)
- `.jsx` entry files are in the esbuild glob in both v15 and v16, so `public/js/foo.bundle.jsx` is compiled by `bench build` without any extra tooling (esbuild handles JSX natively). — [esbuild.js v15 line ~192](https://github.com/frappe/frappe/blob/version-15/esbuild/esbuild.js); [develop](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- After the esbuild pass, with `--run-build-command` (which bench passes on build), esbuild looks at each non-frappe app's root `package.json`; if it has `scripts.build`, it runs `yarn build` in the app root (v15: `execSync("yarn build")` sequentially; v16: `run_app_build` with concurrency, reporting `yarn install`/`yarn build` failures per app and hint `--verbose`). — [esbuild.js v15 run_build_command_for_apps](https://github.com/frappe/frappe/blob/version-15/esbuild/esbuild.js); [develop](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- `NODE_PATHS` for esbuild include each app's `node_modules`, so a dependency declared in the app root `package.json` (e.g. `react`, `react-dom`) can be imported from a `*.bundle.jsx`. — [esbuild.js](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- The hashed outputs are registered in `sites/assets/assets.json` (and `assets-rtl.json`) mapping `"<name>.bundle.js"` to `"/assets/<app>/dist/js/<name>.bundle.<HASH>.js"`; server-side `bundled_asset(path)` and client-side `frappe.assets.bundled_asset(path)` resolve a `.bundle.` name via that JSON. The server caches `assets.json` in Redis unless `developer_mode` is on. — [frappe/utils/jinja_globals.py](https://github.com/frappe/frappe/blob/develop/frappe/utils/jinja_globals.py); [frappe/utils/__init__.py get_assets_json (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/utils/__init__.py); [esbuild.js update_assets_obj](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- Frappe-maintained SPA apps all `.gitignore` the Vite output and the generated www HTML, and keep only source + a root `package.json` whose `postinstall` installs the frontend and whose `build` runs the Vite build: Helpdesk ignores `helpdesk/public/desk`, `helpdesk/public/frontend`, `helpdesk/www/helpdesk/index.html`, `node_modules`; CRM ignores `crm/public/frontend`, `crm/www/crm.html`, `node_modules`. — [helpdesk/.gitignore](https://github.com/frappe/helpdesk/blob/develop/.gitignore); [crm/.gitignore](https://github.com/frappe/crm/blob/develop/.gitignore)
- Root `package.json` examples: Helpdesk `{"postinstall": "cd desk && yarn install", "build": "cd desk && yarn build"}`; CRM `{"postinstall": "cd frontend && yarn install --check-files", "build": "cd frontend && yarn build"}`; Gameplan `{"postinstall": "cd frontend && yarn install", "build": "cd frontend && yarn build"}`; Insights `{"postinstall": "cd frontend && yarn install --check-files --frozen-lockfile", "build": "cd frontend && yarn build && yarn build:islands"}`. — [helpdesk/package.json](https://github.com/frappe/helpdesk/blob/develop/package.json); [crm/package.json](https://github.com/frappe/crm/blob/develop/package.json); [gameplan/package.json](https://github.com/frappe/gameplan/blob/develop/package.json); [insights/package.json](https://github.com/frappe/insights/blob/develop/package.json)

- Frappe Cloud decides whether an app update can be applied by `git pull` without a rebuild via `pull_update_file_filter`: any change to `package.json`, `yarn.lock`, `package-lock.json`, `pnpm-lock.yaml`, `.vue`, `.ts`, `.jsx`, `.tsx`, `.scss` forces a rebuild; `.html/.js/.css` under `/www/` are pull-able, other `.js/.css` are treated as "probably requires build". — [press deploy_candidate.py pull_update_file_filter](https://github.com/frappe/press/blob/master/press/press/doctype/deploy_candidate/deploy_candidate.py)
- Frappe Cloud build steps include a "Install Yarn" pre step (`("pre", "yarn"): "Install Yarn"`), confirming yarn is part of every deploy image. — [press deploy_candidate_build.py](https://github.com/frappe/press/blob/master/press/press/doctype/deploy_candidate_build/deploy_candidate_build.py)
- Frappe Cloud docs (search snippet; page itself unreachable here): a build can fail at `yarn install` with `engine "node" is incompatible with this module, expected a version like ">=18.0.0", but got "16.16.0"`; the fix is to match the bench group's Node version to the app's `engines` field. — [docs.frappe.io/cloud/common-issues/incompatible-node-version](https://docs.frappe.io/cloud/common-issues/incompatible-node-version)
- Frappe framework `develop` (v16) itself declares `"engines": {"node": ">=24"}` and depends on `esbuild ^0.28`, `vue ^3.5`, `bootstrap 4.6.2`, `jquery 3.7.1`, `frappe-charts 2.0.0-rc31`. — [frappe/package.json](https://github.com/frappe/frappe/blob/develop/package.json)
- Reported build failures (search snippets of GitHub issues): frontend `yarn build` can hit Node's default heap limit, fixed with `NODE_OPTIONS="--max-old-space-size=4096"` ([frappe/pilot#471](https://github.com/frappe/pilot/issues/471)); a CRM build was killed with exit 137 after ~700 modules ([frappe/crm#204](https://github.com/frappe/crm/issues/204)); a custom app failed with `vite: not found` (exit 127) until deps were installed first with `cd dashboard && yarn && yarn build` ([forum: Frappe Cloud custom app build fail](https://discuss.frappe.io/t/frappe-cloud-custom-app-build-fail/115543)); Builder 1.35.0 failed on Frappe v16.36.0 Docker build with an unresolved `@framework/ui/telemetry` import from the `link:` package ([frappe/builder#921](https://github.com/frappe/builder/issues/921)).
- In v16 the new `@framework/ui` package lives inside the frappe repo at `apps/frappe/ui`, is "never published to npm", ships raw `.vue/.ts` source, and is consumed by apps as `"@framework/ui": "link:../../frappe/ui"` (relative path symlink); vue/vue-router/frappe-ui are peer deps to avoid duplicate Vue instances. — [frappe/ui/README.md](https://github.com/frappe/frappe/blob/develop/ui/README.md); [helpdesk/desk/package.json](https://github.com/frappe/helpdesk/blob/develop/desk/package.json)
- `bench build` can skip building and reuse cached artifacts (`--using-cached`), in which case `update_assets_json_from_built_assets` copies `**/*.bundle.*.{js,css}` from `<app>/public/dist` into `sites/assets/<app>/dist` and rewrites `assets.json`. This is the path for benches that ship prebuilt `public/dist` (used by bench's app cache). — [esbuild.js](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- Frappe's own `bench build` for the framework can download prebuilt assets from GitHub releases (`assets.tar.gz`) instead of building (`download_frappe_assets`), then `build_missing_files()` builds only bundles missing from `assets.json`. — [frappe/build.py (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/build.py)

### Inferences
- Two viable shipping strategies for a React chart library app, both Frappe-Cloud-safe: (A) "esbuild-native": put `public/js/<name>.bundle.jsx` (importing React from the app root `node_modules`) and let `bench build` compile it; no `scripts.build` needed, only `dependencies` in the root `package.json` (bench runs `yarn install` automatically). (B) "Vite-native": keep a `frontend/` Vite project, root `package.json` with `postinstall` + `build`, output to `<app>/public/<dir>` (gitignored) and reference the hashed files via a manifest you generate (Vite `build.manifest`) or via a fixed filename (`rollupOptions.output.entryFileNames`). Insights' `build:islands` (v16-only) is the Frappe-blessed version of (B) for Desk embedding.
- Committing `public/dist` is not the Frappe-maintained convention (every first-party app gitignores build output), but it is not forbidden: esbuild ignores `public/dist` when globbing entries, and `--using-cached` explicitly consumes prebuilt `public/dist/**/*.bundle.*.js`. Committing a Vite output folder (e.g. `public/frontend`) is a pragmatic fallback if you want installs to work on benches with no Node build, but a build will still run on Frappe Cloud if a root `package.json` with `scripts.build` exists, and `emptyOutDir: true` will overwrite the committed copy.
- Because `pull_update_file_filter` treats `.jsx/.tsx/.ts` changes as rebuild-requiring, every release that touches React source triggers a full image rebuild on Frappe Cloud; keep heavy devDependencies minimal to limit OOM risk, and set `engines.node` honestly (the bench group's Node version must satisfy it).
- React 18 compatibility: nothing in the esbuild pipeline constrains the React version; esbuild's `define` of `process.env.NODE_ENV` is the only thing React needs for production builds. Target `es2017` (v15) means modern syntax is down-leveled, but esbuild cannot polyfill APIs; React 18 needs no polyfills on evergreen browsers.

### Gaps
- Could not read Frappe Cloud's marketplace-specific docs (publishing checklist, whether marketplace review requires a clean `bench build`) because docs.frappe.io was unreachable; the behaviour above is inferred from the open-source press Dockerfile and bench code.
- Exact Node versions offered per Frappe Cloud bench version (v15 vs v16 groups) are not in the sources read; the Dockerfile parameterises `NODE_VERSION` from the release group's dependency table.

## Key Question 2: Adding a custom Desk page and Workspace block that renders a React dashboard; Custom HTML Block capabilities and limits

### Takeaway
In v15 the practical route is a Desk `Page` whose `on_page_load` calls `frappe.require("<name>.bundle.js")` then mounts React into `page.body`; Workspace "Custom Block" widgets render a Custom HTML Block inside an open shadow root with `root_element` provided and global `frappe` reachable (so `frappe.require` works), but they are an admin-authored DocType record (HTML/CSS/JS fields, roles, private flag), not a packaged app artefact. In v16 (develop) Frappe adds a first-class "island" contract (`frappe.ui.mount_island`, Page type "Frappe UI", `__onload.island` for Dashboard / Dashboard Chart) that mounts an app-built Vue bundle in a shadow root; it is Vue-centric (`mountVueIsland`) but the host loop only requires a `mount(el, context)` export.

### Cited Findings
- Desk pages: the page view evaluates the page's script (`frappe.dom.eval(this.pagedoc.__script || this.pagedoc.script)`), registers `frappe.pages[name] = wrapper`, then triggers `on_page_load` and, on every visit, `on_page_show`. — [frappe/public/js/frappe/views/pageview.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/views/pageview.js)
- Server side, `frappe.desk.desk_page.get(name)` loads the `Page` doc, checks `is_permitted()` (page roles) and `page.load_assets()`. — [frappe/desk/desk_page.py](https://github.com/frappe/frappe/blob/develop/frappe/desk/desk_page.py)
- `frappe.require(items, callback)` maps each item through `frappe.assets.bundled_asset()` (resolving `name.bundle.js` to the hashed `/assets/<app>/dist/js/name.bundle.<HASH>.js` from `frappe.boot.assets_json`), injects `<script>`/`<link>` tags into `document.head`, de-duplicates already-executed paths, appends `?v=<version>` to non-bundled same-origin assets, and returns a Promise. It resolves even on load error ("for backward compatibility"). — [frappe/public/js/frappe/assets.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/assets.js)

### Inferences
- For a React library on v15 AND v16 the lowest-risk Desk embedding is: `public/js/<lib>.bundle.jsx` exporting a global (e.g. `window.aibytersCharts = { mount(el, spec), unmount(el) }`), a `Page` whose `on_page_load` does `await frappe.require("<lib>.bundle.js"); window.aibytersCharts.mount(page.body[0], spec)`, and `on_page_show` to refresh. Avoid React Router; use Frappe's `frappe.set_route`/`frappe.get_route()` and `frappe.router.on("change")` instead.
- Custom HTML Block is viable for a React dashboard: the block script runs in page scope (global `frappe`, `frappe.require`, `frappe.call` are available), and `root_element` is an open shadow root; React 18 `createRoot(root_element.querySelector('#mount'))` works inside a shadow root. Limits: the block is a DB record created by an admin (shippable via fixtures), the HTML is sanitized of `<script>`/`<style>` tags, no module scripts, no isolated CSS by default (Desk's `desk.bundle.css` is deliberately linked into the shadow root), events like `focusin`/portals (tooltips rendered to `document.body`) escape the shadow root.
- The v16 island contract is the Frappe-blessed way to appear inside Desk Dashboard/Dashboard Chart and Pages; it is Vue-oriented at the `mountVueIsland` level but the host only needs an ES module exporting `mount(el, context)` and registered in `assets.json` as `<name>.island.js`. A React island could in principle be produced by writing `<name>.island.js` with Vite and registering it, but `buildIslands` (the registration path) assumes Vue/Tailwind/frappe-ui tooling. This is develop-branch (v16) behaviour as of Oct 2026; v15 has none of it.

## Key Question 3: Which Frappe CSS variables a chart library should map to for seamless light/dark theming

### Takeaway
Frappe defines its theme on `:root, [data-theme="light"]` and overrides on `[data-theme="dark"]` (v15 `frappe/public/scss/common/css_variables.scss` + `desk/dark.scss`); the stable, documented-in-source tokens to map are `--text-color`, `--heading-color`, `--text-muted`, `--text-light`, `--bg-color`, `--fg-color`, `--card-bg`, `--subtle-fg`, `--subtle-accent`, `--border-color`, `--dark-border-color`, `--control-bg`, `--primary`, `--gray-50..900`, the `--bg-<color>` / `--text-on-<color>` pairs, and Frappe Charts' own `--charts-*` hooks; the dark override for `--gray-700/800` and `color-scheme: dark` are set in `dark.scss`.

### Cited Findings
- v15 light theme (`:root, [data-theme="light"]`) layout colors: `--bg-color: white; --fg-color: white; --subtle-accent: var(--gray-50); --subtle-fg: var(--gray-100); --navbar-bg: white; --fg-hover-color: var(--gray-100); --card-bg: var(--fg-color); --disabled-text-color: var(--gray-600); --disabled-control-bg: var(--gray-50); --control-bg: var(--gray-100); --control-bg-on-gray: var(--gray-200); --modal-bg: white; --popover-bg: white;` borders: `--border-color: var(--gray-200); --dark-border-color: var(--gray-300); --table-border-color: var(--gray-200); --highlight-color: var(--gray-50);` buttons: `--btn-primary: var(--gray-900); --btn-default-bg: var(--gray-100);` also `--primary-color: var(--gray-900)`, `--brand-color: var(--primary)`, `--card-shadow: var(--shadow-sm)`, `--navbar-height: 48px`, `--padding-xs..2xl`, `--margin-xs..2xl`. — [frappe/public/scss/common/css_variables.scss (version-15)](https://github.com/frappe/frappe/blob/version-15/frappe/public/scss/common/css_variables.scss)

- v15 desk-only variables: `--page-head-height: 60px`, `--skeleton-bg: var(--gray-100)`, `--progress-bar-bg: var(--primary)`, `--error-bg/--error-border`, `--appreciation-*`, `--criticism-*`. — [desk/css_variables.scss (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/public/scss/desk/css_variables.scss)
- Frappe Charts-specific dark hooks exist under `.chart-container` in dark mode: `--charts-label-color: var(--gray-300); --charts-axis-line-color: var(--subtle-fg); --charts-stroke-width: 5px; --charts-dataset-circle-stroke: #ffffff; --charts-tooltip-title/label: var(--charts-label-color); --charts-tooltip-value: white; --charts-tooltip-bg: var(--gray-900); --charts-legend-label: var(--charts-label-color);` and `.heatmap-chart g > rect[fill="#ebedf0"] { fill: var(--gray-700) }`; dark mode also sets `color-scheme: dark` and `::selection` colours. Present in both v15 and develop. — [desk/dark.scss (develop)](https://github.com/frappe/frappe/blob/develop/frappe/public/scss/desk/dark.scss); [v15](https://github.com/frappe/frappe/blob/version-15/frappe/public/scss/desk/dark.scss)
- In `develop` (v16) the `common/css_variables.scss` and `desk/css_variables.scss` files were slimmed to spacing/layout tokens (`--padding-*`, `--margin-*`, `--page-max-width: 900px`, `--navbar-height: 48px`, `--page-head-height: 48px`, `--code-block-bg`, `--btn-height: 28px`, `--input-height: 28px`); the colour tokens (`--text-color`, `--bg-color`, `--card-bg`, `--border-color`, `--primary`) are no longer defined in those two files, i.e. they moved elsewhere in the v16 SCSS tree (not located in this research). — [common/css_variables.scss (develop)](https://github.com/frappe/frappe/blob/develop/frappe/public/scss/common/css_variables.scss); [desk/css_variables.scss (develop)](https://github.com/frappe/frappe/blob/develop/frappe/public/scss/desk/css_variables.scss)
- Desk sets the theme at boot (`this.setup_theme()` in `frappe.Application.startup`) and the `/app` template receives `"desk_theme": boot.get("desk_theme") or "Light"`, i.e. the `data-theme` attribute on `<html>` is set server-side from the user's Desk Theme and may be "Automatic". — [frappe/public/js/frappe/desk.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/desk.js); [frappe/www/app.py (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/www/app.py)
- v16 islands "mirror the host theme" into the shadow root (`mountVueIsland` "opens the shadow root, adopts the app's stylesheet, mirrors the host theme"), and `useHost()` exposes `theme` to components. — [frappe/ui/README.md](https://github.com/frappe/frappe/blob/develop/ui/README.md)

### Inferences
- Recommended mapping for a chart theme object read at mount time via `getComputedStyle(document.documentElement)`: text → `--text-color`, muted labels/ticks → `--text-muted`, headings → `--heading-color`, surface → `--card-bg` (fallback `--fg-color`), page background → `--bg-color`, gridlines/axes → `--border-color` (stronger: `--dark-border-color`), hover/highlight → `--highlight-color` / `--subtle-fg`, tooltip → `--popover-bg` + `--text-color`, accent → `--primary` (fallback `--primary-color`), categorical palette → `--blue-500`, `--green-500`, `--orange-500`, `--purple-500`, `--pink-500`, `--cyan-500` etc. (the `--<color>-NNN` scale exists in both versions since `--bg-*` pairs reference it). Since CSS custom properties inherit into shadow roots, mapping via `var(--token, fallback)` in the library's own CSS works in a Custom HTML Block, a Page, and an island alike.
- Detect dark mode with `document.documentElement.getAttribute("data-theme") === "dark"` and observe attribute changes with a `MutationObserver` (Desk toggles the attribute without reload); because `--gray-700/800` are re-defined in dark mode, charts that hard-code `--gray-NNN` will shift unexpectedly, so prefer semantic tokens.
- Because v16 moved colour tokens out of `css_variables.scss`, a library should never import Frappe SCSS; consume runtime CSS variables only, with sensible fallbacks.

### Gaps
- The v16 location of the colour tokens (`--text-color`, `--bg-color`, `--card-bg`, `--primary`, `--gray-*` palette) was not found (likely `frappe/public/scss/common/` palette files or a generated tokens file); confirm by grepping the installed frappe app before shipping.
- Did not locate the definition of `--primary` / `--shadow-sm` etc. (palette/shadow files) in either branch.

### Inferences
- A React chart-library marketplace app can copy this shape 1:1 with Vite+React instead of Vue: `frontend/` (Vite, `base: /assets/<app>/frontend/`, `outDir: ../<app>/public/frontend`, copy `index.html` to `<app>/www/<route>.html`), `www/<route>.py` injecting boot (`csrf_token`, `session_user`), `website_route_rules` catch-all, and `add_to_apps_screen`. ## Key Question 5: Pitfalls — Desk global CSS leakage, jQuery/Bootstrap conflicts, asset caching, CSP, app_include_js order; plus how Dashboard Chart / Number Card / query_report feed chart data

### Takeaway
Desk ships Bootstrap 4.6 + jQuery 3.7 globally and its `desk.bundle.css` styles bare elements, so a React chart must either live in a shadow root (Custom HTML Block / v16 island) or use scoped class prefixes and explicit resets; asset caching is handled by content hashes for `.bundle.` files and `?v=<version>` for others; Frappe sets no CSP header by default (nothing found in `app.py`/`response.py`), so inline scripts (e.g. Custom HTML Block's injected `<script>`) work out of the box; `app_include_js` loads after Desk's own bundles in installed-app order and cannot be reordered per app. Data for charts comes from three whitelisted endpoints: `frappe.desk.doctype.dashboard_chart.dashboard_chart.get`, `frappe.desk.query_report.run` (report with a `chart` key) and custom `Dashboard Chart Source` methods registered via `frappe.dashboards.chart_sources[name] = { method, filters }`.

### Cited Findings
- Desk's dependency set (develop): `bootstrap 4.6.2`, `jquery 3.7.1`, `popper.js`, `@popperjs/core`, `moment`, `quill`, `vue ^3.5`, `pinia`, `frappe-charts 2.0.0-rc31`, `frappe-datatable`, `highlight.js`, `socket.io-client` — all bundled into Desk and present as globals (`$`, `frappe`, `moment`). — [frappe/package.json](https://github.com/frappe/frappe/blob/develop/package.json)
- Custom HTML Block deliberately injects Desk's `desk.bundle.css` into the shadow root (`link.href = frappe.assets.bundled_asset("desk.bundle.css")`), so Bootstrap/Desk element styles DO apply inside a block even though the shadow boundary blocks everything else. — [frappe/public/js/frappe/dom.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/dom.js)
- v16 islands isolate styles: "`mountVueIsland` opens the shadow root, adopts the app's stylesheet"; "The app ships one stylesheet for all its islands"; overlays "render in the browser's top layer, above the host's chrome whatever stacking context the island sits in" and need the popover API (Safari 17, Chrome 114); reka-ui must be patched "to read the shadow root". — [frappe/ui/README.md](https://github.com/frappe/frappe/blob/develop/ui/README.md)
- Asset caching: esbuild output names are `[name].[hash]` and recorded in `assets.json`; `frappe.require` only appends `?v=` to assets whose path does not contain `.bundle.`; in `developer_mode`/`dev_server` the version string is `Date.now()`, otherwise `window._version_number`. `frappe.assets.check()` clears localStorage page/doctype caches on version change. — [assets.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/assets.js)
- Server-side `get_assets_json()` is cached in Redis (`frappe.cache.get_value("assets_json", ..., shared=True)`) when not in developer mode, so after a build on a production bench the cache must be cleared (bench does this via `bench build`/restart). — [frappe/utils/__init__.py (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/utils/__init__.py)
- v16 esbuild watch mode: rebuilds update `assets.json` and `notify_redis({success, changed_files})` to live-reload Desk (`--live-reload`); the esbuild `build-cleanup` plugin removes stale hashed files. — [esbuild.js](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js)
- Forum (snippet): a developer's changes "weren't picked up until they renamed the file", consistent with stale `assets.json` / Redis cache rather than a browser cache. — [forum: React in Desk Pages ERPNext 15](https://discuss.frappe.io/t/react-in-desk-pages-erpnext-15/123683)
- `app_include_js` order: Desk's `/app` page builds `include_js = hooks.get("app_include_js", []) + frappe.conf.get("app_include_js", [])`; hook lists are concatenated in installed-apps order; site config can append extra files. There is no per-app priority key. — [frappe/www/app.py (v15)](https://github.com/frappe/frappe/blob/version-15/frappe/www/app.py)

### Inferences
- CSS leakage mitigation for a React chart library in a Desk `Page` (no shadow root): Bootstrap 4 resets `svg { overflow: hidden; vertical-align: middle }`, `box-sizing: border-box`, `button`, `table`, `label` margins, and Desk sets `font-size: var(--text-md)` etc.; a library should (a) namespace every class, (b) avoid bare-element selectors, (c) set `box-sizing`, `line-height`, `font-family: inherit` explicitly on its root, and (d) render tooltips/portals inside its own root rather than `document.body` where Desk's `.modal`/`z-index` rules apply. Alternatively mount inside `frappe.create_shadow_element`-style shadow root even on a Page (helper is public and in both versions).
- Because Desk re-links `desk.bundle.css` inside Custom HTML Block shadow roots, a chart library cannot assume a clean cascade there either; it must still win specificity against Bootstrap's element rules (use a wrapper class + `all: initial` style reset on the mount node if needed).
- No CSP means inline `<script>`/`eval` (used by Desk itself for page scripts and chart sources) work; a site admin who adds a strict CSP via nginx will break Custom HTML Block and `frappe.dom.eval` paths long before a hashed `*.bundle.js` loaded via `frappe.require` breaks — so prefer the `Page + frappe.require` path for CSP-hardened sites.
- Data feeding: a React dashboard should call `frappe.xcall("frappe.desk.doctype.dashboard_chart.dashboard_chart.get", {chart_name, filters, refresh})` or `frappe.xcall("frappe.desk.query_report.run", {report_name, filters})` and read `.chart` (Frappe Charts format `{data: {labels, datasets}, type}`), normalising both into the library's series model; a custom `Dashboard Chart Source` (JS + Python pair exported in developer mode) is the way to register the library's own server-side query as a first-class "Custom" chart type that admins can place on Dashboards.
- `app_include_js` order pitfall: if the library bundle is in `app_include_js` and ERPNext/HRMS also add scripts, there is no guarantee of order relative to them; make the bundle self-contained (no dependency on other apps' globals) and lazy-load with `frappe.require` from pages instead of `app_include_js` to avoid adding to every Desk page load.
