# Frappe's marketplace now merges apps same-day

Publishing a Frappe/ERPNext app in late 2026 means satisfying two coexisting systems: the legacy Frappe Cloud dashboard marketplace (cloud.frappe.io/marketplace, backed by the open-source `frappe/press` code) with its `App Release Approval Request` plus an automated six-area "App Auditor" launched in June 2026, and the new GitHub-hosted registry at `github.com/frappe/marketplace` (announced September 2026) where a listing is a pull request and apps "go live immediately without any manual approvals" once schema, Semgrep and a real `bench get-app` install pass ([The New Marketplace](https://discuss.frappe.io/t/the-new-marketplace/164661)). Both systems demand the same artefact: a standalone public GitHub repo, MIT or GPL-compatible, with a root `pyproject.toml` whose `[tool.bench.frappe-dependencies]` declares a bounded Frappe range, a `hooks.py` whose `app_name` matches the package directory, no symlinks, and (for the v2 registry) prebuilt assets published to a GitHub release. Monetisation is open-core by rule, not by choice: paid apps must still be open source, Frappe keeps the first **USD 500** of lifetime revenue and **20 %** thereafter, plans are monthly recurring and pro-rated, and the app detects its plan on Frappe Cloud through an `sk_<app>` secret in `site_config.json` exchanged against `press.api.developer.marketplace.get_subscription_info` ([Payouts](https://docs.frappe.io/cloud/marketplace/payouts); [press site.py](https://github.com/frappe/press/blob/master/press/press/doctype/site/site.py)). Frontend-heavy apps work because Frappe Cloud's build image installs Node and yarn and runs `bench build` on every app, but every first-party SPA gitignores its Vite output and rebuilds in the image, which brings OOM, Node-engine and pnpm-vs-yarn pitfalls; the lowest-risk path for a React library is a committed, self-contained bundle loaded on demand with `frappe.require` into a Desk `Page` and into Workspace Custom HTML Blocks (shadow DOM), with v16 islands as the next step. The competitive field for charts is thin: Frappe Insights is free and AGPL but not embeddable in Desk without a public iframe, the built-in Dashboard Chart has six rigid types, Lumen Reports is the only credible free no-code widget app, and **no self-serve paid dashboard app with a published monthly price exists on the marketplace**. For AI Byters Charts the implications are concrete: ship a separate MIT repo with a committed bundle and no root `package.json` that yarn could choke on, sell Starter/Pro/Enterprise plans at roughly $19/$49/$149 per site per month on Frappe Cloud plus Ed25519 licence keys for self-hosted customers, position as the Desk-native executive layer over existing Reports and Number Cards rather than a BI query engine, and fix two defects in the current scaffold before submission (the build output is gitignored, and the frontend `package.json` uses pnpm `workspace:*` specifiers that Frappe Cloud's yarn cannot resolve).

## Two submission paths coexist, and the GitHub registry is already the fast lane

On the legacy path a publisher enables a publisher account from the Frappe Cloud dashboard settings, adds an app from GitHub (the GitHub App installation must own the repo), picks the Frappe versions each branch supports, and fills a listing whose fields are fixed by the `Marketplace App` doctype: logo, title, a summary capped at **140 characters**, a long description auto-populated from the repo README, screenshots, categories, and five mandatory links (website, support, privacy policy, documentation, terms of service) ([marketplace_app.json](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.json); [Publishing an App to Marketplace](https://docs.frappe.io/cloud/marketplace/publishing-an-app-to-marketplace)). Submitting a release creates an `App Release Approval Request` (statuses Open / Cancelled / Approved / Rejected) which on insert spawns a "Submission Gate" `Marketplace App Audit`; a request can only move to Approved when the audit verdict is Pass or Needs Improvement, and the app can only be Published once at least one release is approved with a passing audit ([app_release_approval_request.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/app_release_approval_request/app_release_approval_request.py); [marketplace_app.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/marketplace_app.py)). Press also runs a periodic nag job that emails the team when the logo is missing, the description still contains the placeholder "Please add a short", any of the five links is empty, or no approval request exists ([events.py](https://raw.githubusercontent.com/frappe/press/master/press/press/doctype/marketplace_app/events.py)).

The human half of that path broke down in 2025–2026. The official SLA was "Apps will be reviewed or published in 10 days time", but forum threads report **more than two weeks** of unchanged status in January 2026, **almost two months** "under review with no clear update" mid-2026, and an app stuck nearly two weeks after fixing the only flagged issue in September 2026 ([How long does it usually take](https://discuss.frappe.io/t/how-long-does-it-usually-take-for-marketplace-to-release-a-version-of-my-app/159324); [Review Delayed (2 Months)](https://discuss.frappe.io/t/marketplace-app-review-delayed-2-months-need-guidance/162144); [App is in Review state](https://discuss.frappe.io/t/app-is-in-review-state-not-publishing/164818)). The volunteer Marketplace Working Group that was supposed to fix this "started with some noise, but soon things started to slow down and then died", citing reviewer capacity ([the story till now](https://discuss.frappe.io/t/marketplace-working-group-the-story-till-now/163183)). Frappe's two answers are the June 2026 automated auditor that "kicks off the moment you publish a new release", scanning six areas and returning Pass / Warn / Needs Improvement / Fail ([Frappe Cloud Release](https://frappe.io/blog/product-updates/frappe-cloud-release-|-deploy-experience-and-more)), and the v2 registry, where a listing is two JSON files (`apps.json` metadata plus `apps/<name>.json` releases pinned to branch and commit), CI runs schema → Semgrep → get-app validator and stops at the first failure, Critical and Major Semgrep findings block the merge, and "once your app passes all automated checks, it goes live immediately" ([frappe/marketplace README](https://github.com/frappe/marketplace); [The New Marketplace](https://discuss.frappe.io/t/the-new-marketplace/164661)). The registry is consumed by `frappe/pilot` (the new bench/server manager) and reaches "every VM whether hosted on Frappe Cloud or self-hosted", which makes it the first distribution channel that also serves self-hosters. Throughput is real: on 19–20 October 2026 roughly a dozen "advertise <sha>" PRs for gameplan, raven and others merged the same day they opened, and Frappe's own gameplan publishes "every merge to develop" through the reusable `publish-release.yml` workflow, which reads `version`, `frappe_core` and `dependencies` from `pyproject.toml` and opens the PR automatically ([frappe/marketplace pulls](https://github.com/frappe/marketplace/pulls?q=is%3Apr); [gameplan PR #616](https://github.com/frappe/gameplan/pull/616)). Third parties are already through: Kamra PMS merged on 12 October 2026 after fixing a release-please version marker and absolute symlinks, with Semgrep reporting 244 advisory and 0 blocking findings ([Kamra-PMS PR #159](https://github.com/Kamra-PMS/kamra-pms/pull/159)).

What remains uncertain is the seam between the two: the registry README says nothing about paid plans or pricing, no official statement says whether v1 submissions are still accepted or when existing listings migrate, and the v2 `apps.json` has no licence field (it enforces a public repo, while the v1 docs enforce the licence). The practical reading is that billing still lives inside Frappe Cloud (press retains the full plan, subscription and payout machinery at its 20 October 2026 HEAD) while discovery and submission move to GitHub, so a publisher who wants paid plans today must do both: list on the dashboard for billing and advertise releases in the registry for distribution.

## The audit codifies exactly what a compliant repo looks like

The auditor and the registry validator turn the old "guidelines" into enforceable checks, and because both are open source the requirements are precise. The table below condenses the blocking and advisory rules from the press audit modules and the registry validator ([versioning.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/versioning.py); [dependencies.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/dependencies.py); [metadata.py](https://raw.githubusercontent.com/frappe/press/master/press/marketplace/doctype/marketplace_app_audit/checks/metadata.py); [get_app_check.py](https://github.com/frappe/marketplace/blob/main/validation/get_app_check.py)).

| Area | Hard requirement (Critical / blocking) | Advisory (Warn) |
|---|---|---|
| `pyproject.toml` | Exists at repo root, valid TOML, has `[tool.bench.frappe-dependencies]` with a valid semver **range** for `frappe` | `frappe`/`erpnext`/`hrms`/`crm` in `[project.dependencies]` (Major, "will cause build failures"); hard-pinned frappe; `requirements.txt` alongside; no version declared |
| Version | v2: advertised `version` equals `[project] version` (fallback `__version__` in `<app>/__init__.py`), `frappe_core` equals the pyproject frappe spec, commit is a full 40-char SHA reachable from `branch` | — |
| `hooks.py` | Exists, parses, `app_name` equals the package directory | `required_apps` not a plain list of string literals; contains `frappe`, duplicates or empty strings |
| Repo hygiene | No symlinks anywhere; no bare calls (e.g. `print()`) at module level in `__init__.py` | `override_doctype_class`, `override_whitelisted_methods`, wildcard `"*"` in `doc_events` |
| Compatibility | Every enabled bench using the source, and the registered Frappe version, must fall inside the pyproject range | — |
| Listing (v1) | Long description present; screenshots present; all five links present | Install instructions (`bench get-app`, `git clone`), the words "architecture/deployment/installation", or any `http(s)://` link inside the long description; broken links; no categories |
| Assets (v2) | A prebuilt `<app>-<sha>.tar.gz` plus `.sha256` in a GitHub release tagged `assets-<branch>` | — |
| Security | Semgrep Critical/Major (code injection, template/SQL injection, command execution, authorization bypass, multitenancy violations) | WARNING-level findings reported, non-blocking |

Branch naming is convention, not rule. Helpdesk advertises a stable 1.30.1 release on `main` with `frappe_core ">=15.116.1,<17.0.0"` and a nightly on `develop` with `">=16.0.0-dev,<18.0.0"`, while blog uses `version-16`; what matters is that each branch's range resolves to the Frappe versions it is registered for, that `channel` (`stable` or `nightly`) "describes the code line, not the branch name", and that Pilot "installs the newest compatible `stable` release" and falls back to nightly only when nothing stable fits ([apps/helpdesk.json](https://github.com/frappe/marketplace/blob/main/apps/helpdesk.json); [frappe/marketplace README](https://github.com/frappe/marketplace)). Because resolution is by `frappe_core` range, a publisher who supports both v15 and v16 keeps one release entry per Frappe major. Nothing in the 2026 sources mentions v14, and the guidelines require supporting "the current stable version of Frappe/ERPNext" ([Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)). Monorepos are out: Frappe Cloud "doesn't support Monorepos", press models each source as a (owner, repository, branch) triple reading README and pyproject from the root, and the v2 validator symlinks the whole clone into a throwaway bench ([Hosting Custom Apps in Monorepo](https://discuss.frappe.io/t/hosting-custom-apps-in-monorepo-on-frappe-cloud-is-it-supported/130028); [get_app_check.py](https://github.com/frappe/marketplace/blob/main/validation/get_app_check.py)).

The listing rules deserve equal weight because they are the most common real-world blocker: the only issue flagged in the September 2026 "stuck in review" thread was install instructions in the long description. The guidelines also want a custom square logo of at least **200×200 px** displayed in a circular frame, a one-sentence summary of 40–80 characters, no repetition of the summary in the long description, screenshots in the screenshot section rather than the description, a short demo video on request, and passing GitHub Actions CI in the repo ([Guidelines for publishing an app](https://docs.frappe.io/cloud/marketplace/marketplace-guidelines)). The README therefore has to be written as marketing copy, not developer documentation, because press copies it verbatim into the long description at insert time.

## Paid apps are open-core by rule: 80/20 after $500, plan detection via a site secret

The licence rule is unambiguous and applies to paid apps: "All apps on the Marketplace must be Open Source... MIT or compatible with the GNU General Public License", hosted on a GitHub repo the publisher owns ([Frappe Cloud Marketplace Overview](https://docs.frappe.io/cloud/marketplace)). The v2 registry's `repo` field is a public GitHub URL cloned anonymously by CI, so even a source-available private repo is excluded technically. A September 2026 forum thread from an independent developer asks what business model is left for standalone commercial products given that "marketplace apps must be open source, including paid apps"; no maintainer answer surfaced ([Genuine question](https://discuss.frappe.io/t/genuine-question-what-is-the-intended-business-model-for-independent-frappe-app-developers/164881)). Legally, an app that depends only on the MIT framework could be proprietary, but anything importing ERPNext (GPL-3.0) or the newer AGPL-3.0 apps (CRM, Helpdesk, Insights) inherits copyleft risk, and in every case it cannot be listed ([Why open source?](https://docs.frappe.io/customer-guide/about-frappe/what-open-source-mean-for-you); [Selling Apps built on frappe](https://discuss.frappe.io/t/selling-apps-built-on-frappe-and-erpnext/78431)).

The economics are a payment-processor model. A `Marketplace App Plan` carries a title, `price_inr`, `price_usd`, a monthly interval, a bullet list of features and version restrictions; the app's `subscription_type` is derived automatically (free and paid plans together make "Freemium") ([marketplace_app_plan.py](https://github.com/frappe/press/blob/master/press/marketplace/doctype/marketplace_app_plan/marketplace_app_plan.py)). "Currently only monthly recurring plans are available. These are charged on pro-rata basis", so a customer on a $30/month plan for ten days pays $10 on their regular Frappe Cloud invoice ([App Pricing Plans](https://docs.frappe.io/cloud/app-plan)). The 2022 launch allowed "a maximum of 3 plans", a cap that no longer appears in code and may be stale ([Grow with Frappe Cloud and Marketplace](https://frappe.io/blog/frappe-cloud/grow-with-frappe-cloud-and-marketplace)). Commission is implemented as `total * Press Settings.commission` only after a cumulative threshold is passed; before that the commission equals the whole amount, which is how "Frappe Cloud takes the first $500" is enforced, and the code's own TODO admits the threshold month is not pro-rated ([marketplace_app_payment.py](https://github.com/frappe/press/blob/master/press/marketplace/doctype/marketplace_app_payment/marketplace_app_payment.py)). Payouts are generated monthly as `Payout Order`s from **paid** customer invoices only, in INR or USD, as cash (PayPal invoice required outside India) or Frappe Cloud credits ([payout_order.py](https://github.com/frappe/press/blob/master/press/press/doctype/payout_order/payout_order.py); [Payouts](https://docs.frappe.io/cloud/marketplace/payouts)). Customers on free credits cannot install paid apps at all ("You cannot install a Paid app on Free Credits") ([press/api/site.py](https://github.com/frappe/press/blob/master/press/api/site.py)). A separate programme shares **25 % of Frappe's top-line hosting revenue** with developers of free apps, weighted by a 1–10 rating of complexity, dependencies and marketing effort, on an opt-in and approval basis ([Revenue sharing with 3rd party apps](https://frappe.io/blog/announcements/revenue-sharing-with-3rd-party-apps-on-frappe-cloud-marketplace)). A low-priced app therefore sees no cash for many months; early pricing should optimise for installs and the free-app pool, not margin.

Plan detection inside the site has no official developer documentation; it is documented only by press source and by example apps. When a paid app is installed, `Site.install_marketplace_conf` creates the subscription and pushes `{"sk_<app>": secret}` into the running site's config; the inline comment at the October 2026 HEAD explains that "Marketplace apps authenticate to the Marketplace Developer API with a per-site secret read from their own site_config as `sk_<app>`" and that `update_site_config` is needed because "arbitrary config changes are not propagated on save" for live sites, which reads as the fix for an injection bug a vendor (`erpnext_easy_cash`) worked around with `USE_PLAN_LIMITS = False  # TODO: Enable after FC fixes sk_ key injection bug` ([press site.py](https://github.com/frappe/press/blob/master/press/press/doctype/site/site.py); [easy_cash plan.py](https://raw.githubusercontent.com/ahmedyousef96/erpnext_easy_cash/main/easy_cash/api/plan.py)). The plan name is never written locally; the app POSTs `{"secret_key": key}` to the guest endpoint `press.api.developer.marketplace.get_subscription_info`, which returns only `document_name`, `enabled`, `plan` and `site`, or to `get_subscription_status` for a bare status; an invalid or disabled key returns HTTP 401 ([press/api/developer/marketplace.py](https://github.com/frappe/press/blob/master/press/api/developer/marketplace.py)). Frappe HR does exactly this with a five-second timeout and gates its SaaS-only behaviour by hostname so self-hosted installs get the full GPL app ([hrms subscription_utils.py](https://raw.githubusercontent.com/frappe/hrms/develop/hrms/subscription_utils.py)). The push-style `subscription_update_hook` is only fired for `erpnext` and `hrms`, so third parties must poll ([marketplace_app_subscription.py](https://github.com/frappe/press/blob/master/press/marketplace/doctype/marketplace_app_subscription/marketplace_app_subscription.py)). For self-hosted customers there is no Frappe licence mechanism at all; observed vendor behaviour is to allow unlimited use off-cloud (easy_cash maps "no key and not on Frappe Cloud" to "Self-Hosted: Unlimited"), to sell off-marketplace at a fixed price with no enforcement (Webkul's Power BI connector at **USD 399** one-off), or to price support tiers rather than features (POS Awesome at **$50 / $100 / $200 per month** differing by support tickets and hours) ([Webkul store](https://store.webkul.com/erpnext-powerbi-connector.html); [POS Awesome listing](https://frappecloud.com/marketplace/apps/posawesome)). No reference implementation of a licence-key server for a Frappe app was found; a vendor who wants one builds it.

## Frappe Cloud builds Node, so the question is whether to let it

Frappe Cloud does run a Node build. Its Docker template installs Node through nvm and yarn globally, runs `bench get-app` for every app in the release group, and `bench get-app` in turn runs `yarn install --check-files` whenever the app root has a `package.json` and then `bench build` ([press Dockerfile](https://github.com/frappe/press/blob/master/press/docker/Dockerfile); [bench app.py](https://github.com/frappe/bench/blob/develop/bench/app.py)). `bench build` does two things: Frappe's esbuild driver globs every app's `public/**/*.bundle.{js,ts,css,scss,jsx}` (ignoring `public/dist`), bundles with content hashes into `sites/assets/<app>/dist/` and records the mapping in `assets.json`, targeting es2017 on v15 and es2020 on v16; then, because bench passes `--run-build-command`, it runs `yarn build` in the root of every non-frappe app whose `package.json` has `scripts.build` ([esbuild.js develop](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js); [esbuild.js v15](https://github.com/frappe/frappe/blob/version-15/esbuild/esbuild.js)). Every Frappe-maintained SPA relies on that second path: Helpdesk, CRM, Gameplan and Insights all gitignore their Vite output and the generated `www/*.html`, and keep a root `package.json` whose `postinstall` installs the `frontend/` project and whose `build` runs Vite into `<app>/public/<dir>` with `base=/assets/<app>/<dir>/` ([helpdesk .gitignore](https://github.com/frappe/helpdesk/blob/develop/.gitignore); [insights package.json](https://github.com/frappe/insights/blob/develop/package.json); [frappe-ui buildConfig.js](https://github.com/frappe/frappe-ui/blob/main/vite/buildConfig.js)). The cost of that convention is visible in the issue trackers: Vite builds hitting Node's default heap limit until `NODE_OPTIONS="--max-old-space-size=4096"` is set, a CRM image build killed with exit 137 after ~700 modules, `vite: not found` when dependencies were not installed before `yarn build`, a Builder release failing on Frappe v16.36.0 over an unresolved `link:` package, and the documented Frappe Cloud failure `engine "node" is incompatible with this module` when the bench group's Node version does not satisfy the app's `engines` field ([pilot #471](https://github.com/frappe/pilot/issues/471); [crm #204](https://github.com/frappe/crm/issues/204); [builder #921](https://github.com/frappe/builder/issues/921); [Incompatible Node version](https://docs.frappe.io/cloud/common-issues/incompatible-node-version)). Any change to `package.json`, lockfiles or `.jsx/.tsx/.ts/.vue/.scss` files forces a full image rebuild on Frappe Cloud rather than a `git pull` update ([deploy_candidate.py](https://github.com/frappe/press/blob/master/press/press/doctype/deploy_candidate/deploy_candidate.py)). Committing a prebuilt bundle is not the first-party convention but nothing forbids it: esbuild ignores `public/dist` when globbing entries, `bench build --using-cached` explicitly consumes prebuilt `public/dist/**/*.bundle.*` files, and the v2 registry itself now distributes prebuilt tarballs from `assets-<branch>` releases so benches download instead of building ([esbuild.js](https://github.com/frappe/frappe/blob/develop/esbuild/esbuild.js); [helpdesk assets-main](https://github.com/frappe/helpdesk/releases/tag/assets-main)). The practical rule is binary: if the repo has no root `package.json`, Frappe Cloud runs no Node step for the app and whatever is committed is served; if it has one with `scripts.build`, the build runs and `emptyOutDir: true` overwrites the committed copy.

Embedding in Desk has three tiers of maturity. On v15 and v16 alike the reliable path is a Desk `Page`: the page view evaluates the page script and calls `on_page_load`, where `await frappe.require("<lib>.bundle.js")` resolves hashed bundles through `assets.json` (and appends `?v=<version>` to non-bundled paths), after which React mounts into `page.body` ([pageview.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/views/pageview.js); [assets.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/assets.js)). DoppioBot shipped "ChatGPT in the Desk, powered by React" this way, and forum guidance is consistent: React Router cannot be used because Desk owns routing ([doppio_bot README](https://github.com/NagariaHussain/doppio_bot/blob/main/README.md); [React in Desk Pages ERPNext 15](https://discuss.frappe.io/t/react-in-desk-pages-erpnext-15/123683)). Workspace embedding goes through the `Custom HTML Block` doctype (HTML, JS, CSS, roles, private flag), which the widget renders with `frappe.create_shadow_element`: an open shadow root into which Desk deliberately re-links its own `desk.bundle.css`, an IIFE that exposes `root_element`, global `frappe` available, and `<script>`/`<style>` stripped from the HTML field ([dom.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/dom.js); [custom_html_block.json](https://github.com/frappe/frappe/blob/version-15/frappe/desk/doctype/custom_html_block/custom_html_block.json)). Blocks are database records, so an app ships them as fixtures or creates them from a DocType action; non-admins can only create private blocks. The v16 `develop` branch adds a first-class island contract: "An island is a Vue UI unit. An app builds it, and a host mounts it in a shadow root", registered in `assets.json` as `<name>.island.js`, mounted with `frappe.ui.mount_island(name, el, props)`, usable as a `Page` of type "Frappe UI", and able to take over Desk's `Dashboard` and `Dashboard Chart` documents via `doc.set_onload("island", ...)`, exactly as Insights now does with a 1.65 MB budget and a ban on `socket.io-client` ([frappe/ui README](https://github.com/frappe/frappe/blob/develop/ui/README.md); [insights desk.py](https://github.com/frappe/insights/blob/develop/insights/desk.py); [chart_widget.js](https://github.com/frappe/frappe/blob/develop/frappe/public/js/frappe/widgets/chart_widget.js)). The host loop "imports nothing: not Vue, not frappe-ui, not frappe" and only requires a module exporting `mount(el, context)`, so a React island is feasible, but the build helper `buildIslands` assumes Vue tooling, and whether `Page.type = "Frappe UI"` has shipped in a tagged v16 release rather than only `develop` is unverified ([ui/island/host.js](https://github.com/frappe/frappe/blob/develop/ui/island/host.js)).

Theming and data feeds are stable across versions. Frappe sets `data-theme` on `<html>` server-side from the user's Desk Theme and toggles it without reload; v15 defines the semantic tokens on `:root, [data-theme="light"]` (`--text-color`, `--heading-color`, `--text-muted`, `--bg-color`, `--fg-color`, `--card-bg`, `--subtle-fg`, `--border-color`, `--dark-border-color`, `--control-bg`, `--primary`, the `--bg-<color>`/`--text-on-<color>` pairs) and overrides them in `[data-theme="dark"]`, where it also redefines `--gray-700/800`, sets `color-scheme: dark`, and exposes Frappe Charts hooks such as `--charts-label-color` and `--charts-tooltip-bg` ([css_variables.scss v15](https://github.com/frappe/frappe/blob/version-15/frappe/public/scss/common/css_variables.scss); [dark.scss](https://github.com/frappe/frappe/blob/develop/frappe/public/scss/desk/dark.scss)). In `develop` the colour tokens moved out of those two files to an unlocated spot, so a library must consume runtime CSS variables with fallbacks and never import Frappe SCSS. Three whitelisted endpoints feed charts: `frappe.desk.doctype.dashboard_chart.dashboard_chart.get` (returns `labels`, `datasets`, and on develop `dates`), `frappe.desk.query_report.run` (returns `columns`, `result`, `chart`, `report_summary`), and custom `Dashboard Chart Source` methods registered through `frappe.dashboards.chart_sources[name] = { method, filters }`, which can only be created in developer mode ([dashboard_chart.py](https://github.com/frappe/frappe/blob/develop/frappe/desk/doctype/dashboard_chart/dashboard_chart.py); [query_report.py](https://github.com/frappe/frappe/blob/develop/frappe/desk/query_report.py); [dashboard_chart_source.py](https://github.com/frappe/frappe/blob/develop/frappe/desk/doctype/dashboard_chart_source/dashboard_chart_source.py)). Pitfalls worth naming: Desk ships Bootstrap 4.6 and jQuery 3.7 globally and styles bare elements, so a library in a Page needs namespaced classes and explicit resets, while in a Custom HTML Block it still has to beat Bootstrap because `desk.bundle.css` is re-linked inside the shadow root; `assets.json` is cached in Redis outside developer mode, which explains the forum report of changes not appearing "until they renamed the file"; Frappe sets no Content-Security-Policy header, so inline scripts work, but a site admin who adds a strict CSP will break Custom HTML Blocks and `frappe.dom.eval` before a hashed bundle loaded via `frappe.require`; and `app_include_js` is concatenated in installed-app order with no per-app priority, so lazy-loading from pages is safer than global inclusion ([frappe package.json](https://github.com/frappe/frappe/blob/develop/package.json); [frappe/utils/__init__.py](https://github.com/frappe/frappe/blob/version-15/frappe/utils/__init__.py); [www/app.py v15](https://github.com/frappe/frappe/blob/version-15/frappe/www/app.py)).

## Chart apps compete with a free giant that cannot live inside Desk

Frappe Insights is the incumbent: AGPL-3.0, roughly 1.0k stars, a Vue plus frappe-ui plus ECharts SPA with Ibis composing SQL against MySQL, PostgreSQL, DuckDB and BigQuery, listed free on the marketplace with **15.0k–31.5k installs** depending on crawl date, supported on v15 and v16, and shipping releases weekly (v3.15.1 on 20 October 2026, with v3.14.4 noting it "passed the marketplace Semgrep check") ([frappe/insights](https://github.com/frappe/insights); [insights releases](https://github.com/frappe/insights/releases); [Insights listing](https://cloud.frappe.io/marketplace/apps/insights)). Its weakness is precisely where a Desk-native library lives: embedding an Insights dashboard in a Workspace required making it **public with no authentication**, and role-based sharing of embeds was ruled out ([Insights embedding thread](https://discuss.frappe.io/t/frappe-insights-embedding-or-sharing-dashboard-just-for-frappe-users-or-to-a-certain-role/115788)); users report queries timing out at ~250,000 rows, charts limited to the first ten rows, and a v2→v3 break where "there's no way to migrate queries/dashboards" until v3.13.0 added a partial migration ([slow query thread](https://discuss.frappe.io/t/frappe-insights-query-loading-extremely-slow-and-timing-out/157562); [v2 to v3 export](https://discuss.frappe.io/t/export-queries-from-v2-to-v3/147503)). Frappe monetises Insights only through hosting (sites from $5/month), so nobody wins on price against it; the win is fit. The built-in Dashboard Chart has exactly six visual types (Line, Bar, Percentage, Pie, Donut, Heatmap), one colour, and report-based widgets that cannot take runtime filters, and the two liveliest framework issues of 2025–2026 are a request for a Dashboard/Chart Workspace block (opened October 2025, moved to the frappe repo October 2026, still open) and a complaint that chart configuration is "too rigid, with no way to choose or customize X- and Y-axis fields" ([dashboard_chart.json](https://raw.githubusercontent.com/frappe/frappe/version-15/frappe/desk/doctype/dashboard_chart/dashboard_chart.json); [frappe #44001](https://github.com/frappe/frappe/issues/44001); [frappe #44059](https://github.com/frappe/frappe/issues/44059); [frappe #43352](https://github.com/frappe/frappe/issues/43352)).

Third-party competition is thin and mostly free. Lumen Reports is the closest analogue: free, v15 and v16, "19 widget types in light and dark themes", drag-and-drop, an AI query mode, and a trust claim that it "never runs raw SQL... compiles through Frappe's own permission layer" ([Lumen Reports listing](https://cloud.frappe.io/marketplace/apps/lumen_reports)). The only paid analytics listing found, Niyu Labs' BigQuery Connector, hides its price; everything else is either a services engagement dressed as an app (ECOSIRE's dashboard pack and Power BI connector "from $249–$299", quote-based, 2–4 week delivery) or a stale GitHub project ([frappe_bigquery](https://cloud.frappe.io/marketplace/apps/frappe_bigquery); [ECOSIRE BI pack](https://ecosire.com/apps/erpnext/advanced-bi-dashboards-pack)). Confirmed unfilled gaps are charts and KPIs inside Workspaces without public iframes, executive-grade visuals beyond six types (waterfall, bullet, funnel, diverging, slope and the like appear in neither built-ins nor Lumen's described set), dashboard print and PDF, role-scoped embedded dashboards, runtime filters on report charts, and mobile-first layouts ([v13 print dashboard](https://discuss.frappe.io/t/v13-print-dashboard/65243); [Superset recommended thread](https://discuss.frappe.io/t/dashboards-in-frappe-that-offer-power-bi-like-interactive-and-visual-experience/163120)). White-label and enterprise licensed packs have no demand evidence in either direction and should be treated as hypotheses. Listing copy that works follows a `<Brand> <Noun>` name, a "for Frappe and ERPNext" tagline, explicit v15/v16 and free/paid badges in the first line, an Analytics category, and permission-safety claims in the description.

## What this means for the AI Byters Charts app

The evidence resolves most open decisions, and it also exposes two defects in the current `apps/frappe-app` scaffold that would fail the audit or the Frappe Cloud build. The decisions below are stated as positions, with the reasoning compressed.

| Decision | Position | Why |
|---|---|---|
| Repo | Standalone public repo `aibyters_charts`, MIT, exported by subtree split; the monorepo stays proprietary | Monorepos are unsupported by press and the v2 validator; the marketplace requires MIT/GPL-compatible and a publicly cloneable repo |
| Monetisation | Open-core: free tier in the app, Frappe Cloud Marketplace App Plans for hosted customers, Ed25519 licence keys for self-hosted; sell the `@aibyters/*` npm packages separately under the existing proprietary terms | Paid apps must be open source; no Frappe licence mechanism exists off-cloud; the `license.py` dual path already matches the hrms/easy_cash pattern |
| Bundle | Committed, self-contained `public/dist/aib-dashboard.js` + `.css` built from the monorepo; **no root `package.json`** in the exported repo | Removes Frappe Cloud's Node build entirely (no OOM, no `engines`, no yarn/pnpm mismatch); esbuild ignores `public/dist`; every `.jsx` change would otherwise force an image rebuild |
| Desk embedding now | Desk `Page` `/app/aib-dashboard/<name>` loading the bundle with `frappe.require`, plus Workspace Custom HTML Blocks created from the AIB Dashboard form (shadow root) | Works identically on v15 and v16; targets issue #44001 directly; CSP-hardened sites still work through the Page path |
| Desk embedding next | A v16 island (`aibyters_charts.dashboard.island.js`) exporting `mount(el, context)`, and a `Dashboard Chart` claim via `__onload.island` | Frappe-blessed shadow-root isolation and Dashboard takeover; verify it exists in a tagged v16 before depending on it |
| Theme | Map `--vi-*` tokens to Frappe semantic variables at mount with fallbacks; observe `data-theme` with a MutationObserver; never import Frappe SCSS | v16 moved the colour tokens; dark mode redefines `--gray-700/800` |
| Data | Consume `dashboard_chart.get`, `query_report.run`, Number Card `get_result`, and `frappe.get_list` aggregations as the logged-in user; no raw SQL | Semgrep blocks SQL injection and authorization bypass; Lumen's "never runs raw SQL" copy sets the trust bar |
| Positioning | "Executive dashboards inside Desk" that render existing Reports, Charts and Number Cards; not a query engine | Avoids Insights' hard data-layer problems and Lumen's no-code-builder ground; owns Workspace-native, print/PDF, 60+ types, mobile |
| Prices | Free $0 (3 dashboards × 6 widgets); Starter **$19 / ₹1,599**; Pro **$49 / ₹3,999**; Enterprise **$149 / ₹11,999** per site per month; self-hosted keys at roughly 10× the monthly price per site per year | Sits between the $5 hosting floor and POS Awesome's $50 entry, well under ECOSIRE's $249+ anchors; three paid plans respects the historical cap |

The two scaffold defects are concrete. First, the root `.gitignore` rule `dist` currently ignores `apps/frappe-app/aibyters_charts/public/dist`, so the subtree export would ship an app with no JavaScript; add a negation (`!apps/frappe-app/aibyters_charts/public/dist/`) or rename the output directory to something like `public/aib/`. Second, `apps/frappe-app/frontend/package.json` depends on `@aibyters/*` with `workspace:*` specifiers; if that `frontend/` folder or any root `package.json` with `scripts.build` is exported, Frappe Cloud's `yarn install --check-files` will fail on pnpm-only protocol strings and the deploy will not complete. The export script must exclude `frontend/` entirely, which is consistent with the no-root-`package.json` decision above. Three further adjustments follow from the audit rules: the bundle file is not a `*.bundle.js` entry and will not appear in `assets.json`, so the Page must `frappe.require("/assets/aibyters_charts/dist/aib-dashboard.js")` by fixed path and rely on Frappe's `?v=<version>` cache-busting, bumping the app version on every release; the README that doubles as the long description must drop the five `https://` links and any install wording (links go in the listing fields, and the auditor warns on any URL in the description); and the v2 registry's requirement for an `assets-<branch>` release tarball means either calling Pilot's reusable `app-assets.yml` workflow (whose behaviour on an app with no Node build is unverified) or producing the `<app>-<sha>.tar.gz` plus `.sha256` from the committed `public/` folder in the release workflow, which should be tested against the registry CI locally before the first PR, as Kamra did. The licence module should additionally cache the Frappe Cloud lookup in `frappe.cache` with an hourly TTL and refresh it from the existing daily scheduler event rather than on request, fail open to the free tier only when `on_frappecloud()` is true, and treat "no key, not on Frappe Cloud" as a self-hosted site that needs a vendor key rather than as unlimited, because the free tier already guarantees charts always render.

Release mechanics should be dual-track until Frappe states otherwise: register the app on the Frappe Cloud dashboard with one `Marketplace App Version` row per branch (`version-15` with `>=15.0.0,<16.0.0`, `main` with `>=16.0.0,<17.0.0`, rather than the current single `>=15.0.0,<17.0.0` range, so each Frappe major resolves to the branch that was actually tested on it), create the three paid plans there, and submit each release for the auditor; in parallel, add `publish-release.yml` to the standalone repo so every tagged commit opens a registry PR with the matching `version` and `frappe_core`. The Semgrep rules that block are injection and permission bypass, so keep every data path through `frappe.get_list`, `frappe.db.get_value` and `query_report.run` as the session user, avoid `ignore_permissions=True` on any whitelisted method, and run the registry's own `validation/` scripts locally before submission.

## Conclusion

The marketplace has quietly flipped from a gatekept catalogue into a CI-gated package registry, and that changes what "publishable" means: the hard part is no longer getting a human to look at the listing within two months but producing a repo that passes a deterministic audit and installs in a throwaway bench without a build step. Apps that lean on Frappe Cloud's Node build inherit the fragility that Frappe's own SPAs show in their issue trackers, while an app that ships a committed bundle and nothing for yarn to run becomes the simplest possible artefact for both the auditor and Pilot, and that simplicity is itself a competitive advantage for self-hosters who will now discover apps through the same registry.

The commercial picture is equally clear once the open-source rule is accepted rather than fought. Nobody in the ecosystem sells a chart layer; Frappe gives away the BI engine; the money is in Desk-native convenience, polish and support, collected through plans Frappe bills for you and through keys you sell yourself. The uncertainty worth watching is the v2 registry's silence on paid plans: if Frappe Cloud v2 eventually bills from registry metadata, the dashboard-side plan setup becomes legacy, but the `sk_<app>` detection path and the open-core split survive either way.
